01一句话结论

决定「关掉一个 infra 节点会不会掉请求」的，按重要性排序是：节点是怎么关的 → 请求有没有发出去 → 摘流有多快 → 最后才轮到 L4 还是 L7 探测。

L4 与 L7 探测在「节点真 down」这一类故障上完全等价（同时刻失败、同耗时摘流、同样不掉）。差别只在盲区：三次握手成功但数据面不工作时，L4 判健康，非幂等请求直接 502。

02失败是怎么产生的

整份实验只有一条因果链。所有 502、所有长尾，都能归到「失败发生在哪个阶段」上。

同一张图解释了三个看起来矛盾的结果：为什么 connect 超时只是慢、为什么硬 crash 会真掉、为什么 drain 一个都不掉（drain 让节点先摘 endpoint，压根不进入 ①②③ 任何一条）。

由此得到的三条推论

  • 把 proxy_connect_timeout 从 3s 降到 500ms，是把「① 慢」的代价上限直接按比例缩小：p95 从 3006ms 变成 19ms。
  • 爆炸半径 ≈ 在飞请求数 × 1/N(infra 节点数)。5 并发 / 2 节点 → 2 个；20 并发 → 10 个。想「硬 crash 也不掉」，只能靠幂等键 + 客户端重试，或者把下线变成 drain。
  • 非幂等请求的 502 不能靠 LB 参数消除，只能靠「不让在飞请求被切」——也就是先摘流、等排空、再关。

03方案：三层职责

整套配置只服务一个不变量：上游 LB（实验里的 nginx-external，生产里的 BGP/ECMP）接流量的每一个节点，本节点必须至少有一个 Ready 的 ingress pod。因为 externalTrafficPolicy: Local 下，节点没有本地 endpoint 时 kube-proxy 对该节点的 NodePort 是静默 DROP，不是 RST。

k8s 层 · 保证每个节点都有 endpoint

调度与容量

nodeAffinity 硬约束 + taint 决定「在哪」；replicas = 3×N + topologySpread maxSkew=1 / DoNotSchedule 决定「每个都有且均匀」；PDB minAvailable: 50% 决定「维护时不归零」。宁可 pod Pending，也不要 6/0 分布——那样一半流量进黑洞。

LB 层 · 保证没 endpoint 的节点不接流量

探测与超时

L7 探 :31000/healthz（不带业务 Host 头，否则被 ingress 规则抢走），interval 2s / fail 2 / ok 2；proxy_connect_timeout 500ms、read 10s、next_upstream_tries 2；成员文件原子替换、永不为空。

节点层 · 计划内维护自己摘流

把黑洞变成 RST

iptables -t nat -I PREROUTING 1 --dport 31000 -j DNAT --to <nodeIP>:1，让内核自己回 RST。LB 探测从「等 connect 超时」变成「立刻失败」，摘流从 22s 降到 4s，且不动 LB 一行配置。

让节点侧摘流真正生效的那两行

实测反直觉的一条：静态池下节点侧摘流完全不起作用——LB 一直复用已有的上游 keepalive 连接，插了摘流规则后 conntrack 计数 70s 都不降。加上这两行后 12s 归零。已写进 nginx/conf/nginx.conf.tmpl。

upstream k8s_ingress_nodeport {
    least_conn;
    include /etc/nginx/upstream/nodeports.conf;  # 原子替换，永不为空
    keepalive          64;
    keepalive_time     10s;   # ← 关键：不限制寿命，节点侧摘流就是空操作
    keepalive_requests 20;
}
proxy_connect_timeout       500ms;
proxy_read_timeout          10s;      # 默认 30s 会让半开连接卡满 30s
proxy_next_upstream         error timeout http_502 http_503 http_504;
proxy_next_upstream_tries   2;
proxy_next_upstream_timeout 5s;       # 必须 > 业务最长正常响应时间，否则反而制造 502

外加一个外挂探测循环，支持三个名单：manual_down.list（人工下线）、manual_hold.list（维护中不摘）、可用节点为 0 时拒绝应用。单一写入者原则：维护脚本只写名单，落盘和 reload 由健康检查做——否则每次维护会多两次 reload。

04最终推荐流程

思路：计划内维护在节点侧摘流，不碰 LB、不 reload；主动摘流只留给非计划故障，并在维护期间用 hold 名单抑制它。唯一要记的命令：

./scripts/graceful-reboot-infra.sh <node> [wait-conn-seconds]

[1/8] cordon
[2/8] 写 manual_hold（告诉 LB 别摘，省两次 reload）+ 节点侧 nat 摘流(RST)
[3/8] 等 conntrack 连接数 = 0            # 用 conntrack，不能用 ss：NodePort 是 DNAT，没有本地 socket
[4/8] drain --grace-period=60           # endpoint 先摘，在飞请求跑完
[5/8] reboot                            # 不要在 reboot 前删 nat 规则：会留下 kube-proxy DROP 黑洞
[6/8] 等节点 Ready
[7/8] 先 uncordon                       # cordon 状态下 pod 永远 Pending
[8/8] 等 /healthz 连续 2 次通过 → 解除 hold   # 加回要慢

所有行都是 CONC=20、POST、后端 1s、约 5600 请求，同一集群同一拓扑，只换流程和 LB 配置。F 在计划内维护上做到了极致，代价全在非计划故障——这就是 G 保留主动摘流的原因。

什么时候仍然需要 LB 预摘流（C）：不能 drain（必须硬关机）／摘流信号是静默 DROP 而不是 RST／LB 动态摘除成本高（BGP 撤销慢、reload 慢、探测间隔大）。三条都不沾时，预摘流是净成本：多两次 reload，客户端断连从 3 涨到 8。

这就是「凭什么买商业 LB」的量化回答：开源能做对，但要求你同时掌握节点侧（自己摘流）和客户端（重试）两个前提。商业/动态后端 LB 卖的是把这两个前提拿掉。

代价模型（修正版）

一次 reload 杀掉的客户端连接数 ≈ 当时的空闲 keepalive 连接数
                              = 总连接数 × 空闲比例
                              = 总连接数 × (1 − 1/连接池大小)

每 client 1 条连接：空闲比例 ≈ think/(slow+think) ≈ 9% ⇒ 只打断几个。每 client 20 条：任意时刻 19/20 空闲 ⇒ 几乎整个连接池被杀。真实（非同步）流量下就是后者。

06被推翻的结论

这是三份文档最有价值、也最难读的部分：结论按时间顺序追加，前面的原文不删，后面的推翻写在后面。集中列出来。

维护必须先做 LB 预摘流
→
救回在飞请求的是 k8s 侧的 drain。NodePort + ETP=Local 下 drain 让 NodePort 立刻回 RST，LB 探测 3s 内自己就摘了；预摘流只是多两次 reload。
证据 T10：B 组（完全不碰 LB）502 = 0，客户端断连 3；C 组（预摘流）502 = 0，断连 8。
每次 reload 固定打断约 3 个客户端连接
→
≈ 空闲 keepalive 连接数，与连接池大小成正比。低连接数下的「固定 3 个」是抽样错误。
证据 T12：2000 连接下 3808 个请求失败（12.1%），100/100 个 client 全部命中。
节点侧插摘流规则就够了
→
静态池下完全无效：LB 复用旧连接，conntrack 70s 不降。必须配 keepalive_time / keepalive_requests 限制上游连接寿命。
加两行后 12s 归零，1440 请求全 200、0 次 reload。
iptables -j REJECT 放 filter INPUT 就能摘流
→
空操作。kube-proxy 的 DNAT 在更早的 nat PREROUTING，包到 INPUT 时 dport 已是 podIP:80。可用形式是 nat PREROUTING 抢在 kube-proxy 之前 DNAT 到一个没人监听的端口。
实测插了规则后 wget :31000/healthz 仍 200；REJECT 放 mangle PREROUTING 被内核拒（Invalid argument）。
L4 探测和 L7 等价，用哪个都行
→
只在「节点/端口不可达」上等价。「三次握手成功但数据面不工作」L4 全部误判健康，此时 GET 被重试掩盖、非幂等直接 502。
证据 T6（等价）与 T7（盲区，POST 6% 真掉）。
并发越高，故障影响率越高
→
反了。CONC=20 → 0.11%，CONC=100 → 0.043%：断连数取决于「reload 瞬间有多少空闲客户端连接」，与请求速率无关。
证据 T11；相位分析显示被断的 12 个请求，上一个都恰好在 reload 前 100.9–102.3ms 结束。

顺带修掉的两个真 bug

  • 候选列表非原子重写：kubectl ... > nodes 会先把文件截断成 0 字节，容器里的健康检查读到空 → 空 upstream → no live upstreams → 恢复阶段 10 个 502。改成 tmp + mv，并加「空列表跳过本轮」保护。
  • 两个写入者互相覆盖：维护脚本写的 down 会被健康检查下一轮重写，多一次 reload；顺序反了还会把两个节点全标 down，入口直接 502。改成单一写入者：脚本只写名单，健康检查唯一落盘。
